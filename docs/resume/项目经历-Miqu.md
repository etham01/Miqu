# Miqu「觅取」社交系统 —— 简历项目经历（业务理解版）

> 版本取向：**弱化技术实现，突出业务理解**。
> 适合投测试 / QA / 产品转测试 / 业务分析方向的岗位。
> 数据均为仓库实测：11 张表 / 16 个 Controller / 50 个 REST 接口 / 20+ 前端页面；
> 539 条自动化用例（JUnit 291 + pytest 248）+ 12 项浏览器断言，0 失败。

---

## 主用版本（4 条 + 结果行）

**Miqu「觅取」社交系统** ｜ 个人项目 ｜ SpringBoot3 + Vue3 前后端分离
覆盖注册登录、用户关系、私信通知、动态评论、后台管理 5 大模块，11 张表 / 50 个 REST 接口。

- **先把业务规则说清楚，再谈怎么测**：把「互关才能私聊」「不能给自己点赞」「被封禁账号不可交互」这类散落在需求里的口语化描述，整理成 98 条可核对的规则清单，明确每条规则的边界与例外情形，再据此推导用例——避免只按接口签名测，而不是按业务语义测。

- **能识别规则里没说出口的那半句**：验证「互关私聊」时确认到，这条规则限制的是**发起**而不是**查看**——非互关双方不能发新消息，但已有会话的历史消息仍可正常读取和标记已读；且被拒的发送不会留下会话、未读、消息任何残留数据。这种"限制到哪一步为止"的语义，只看接口定义是判断不出来的。

- **用判定顺序验证异常场景**：梳理出一条消息从发出到落库要依次经过参数格式 → 业务身份 → 目标账号状态 → 双方关系四道校验，并验证每道校验被触发时都返回了对应的业务错误提示，而不是笼统报错——确认各异常分支互不掩盖、提示信息对用户可理解。

- **遇到疑似缺陷先核对业务定义，再下结论**：发现"取消关注后仍能看到对方动态"的疑似问题，没有直接判定为 Bug，而是先回到业务定义，确认「关注流」指的是**当前关注关系**而非**历史关注过**，最终**证伪**该问题；同时验证关注 / 取关、点赞 / 取消的往返操作与重复操作不会产生脏数据，取消后可以重新关注、重新点赞。

- **结果**：539 条自动化用例全部通过，覆盖 50 个接口的全部业务分支；验证过程中发现并推动修复 3 处筛选切换后标签与数据不一致的问题、1 处头像地址可填入外部链接的问题。

## 还想要一条讲"覆盖面"和"权限"时（可选第 5 条）

## 改写时留下的几条备注

1. **不要写「简易的社交系统」**。实际是 11 张表 / 16 个 Controller / 50 个接口 / 20+ 页面，写"简易"是自己给自己打折。
2. **用例数用 539**（JUnit 291 + pytest 248），不要写 490——490 对不上任何真实计数，被追问"怎么算的"会很难看。
3. **"98 条 YAML 用例"改说成"98 条业务规则清单"**。同一个东西，前者像技术实现，后者直接体现业务梳理能力。
4. **技术名词只留技术栈那一行**（SpringBoot3 / Vue3）。中间四条的动词尽量用「梳理、确认、验证、厘清、核对」这类业务动作，而不是「编写、搭建、实现、部署」。
5. **"证伪一个缺陷"这条尽量保留**。它是整段经历里最能证明"不是机械执行用例"的一条——能判断"这是预期行为还是缺陷"，靠的是业务理解而不是技术。
