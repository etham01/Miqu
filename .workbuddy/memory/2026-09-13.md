# JMeter 性能测试方案（同日）

用户要求为 Miqu 设计 JMeter 性能测试过程并写成文档。

## 交付
- `docs/testing/PERFORMANCE_TEST_PLAN.md` —— 完整压测方案（0~9 步 + 附录 + CHECKLIST）
- `tests/perf/users.csv` —— 18 个种子账号（test001~test018 / 123456）

## 方案要点（自研设计，非模板套用）
- **压测前三处必改配置**：`mybatis-plus.configuration.log-impl` 默认是
  `StdOutImpl`（每条 SQL 打标准输出，不关掉测的是日志性能）；`logging.level.com.miqu: debug`；
  堆内存 README 推荐的 `-Xmx320m` 是开发省内存用的，压测要给 `-Xms512m -Xmx1g -XX:+UseG1GC`。
  均用**命令行参数覆盖，不改文件**
- **本项目最大的断言坑**：HTTP 恒 200、业务码在 body —— 只断言 HTTP 状态码会得到
  "0% 错误率"的假报告。必须用 JSON 断言 `$.code == 200`；点赞场景放宽为正则 `200|409`
- 五轮场景：基准 → 阶梯加压找拐点 → 混合场景(60/20/15/5 读多写少) →
  稳定性 Soak 30~60min → **并发点赞专项**（50 线程 rampup=0，验证唯一键兜底恰好 1 行）
- **本项目最可能的瓶颈**：`spring.datasource.hikari.maximum-pool-size: 20`。
  文档要求"分情况讨论"而非直接调大——DB 有富余才调池，DB 已高负载则调大只会更慢
- 强调非 GUI 模式跑压测（`jmeter -n -t ... -l ... -e -o report/`），压测时删掉"察看结果树"

## 环境事实（已核实，后续复用）
- 端口 **8081**（8080 被本机 ApplicationWebServer.exe 占用）
- 登录：`POST /api/auth/login`，body `{username,password}`，token 在 **`$.data.token`**
- 分页参数：`page` / `size`，**size ∈ [1,50]**，越界返 400
- 白名单：register / login / health + 动态与用户主页的 GET 路径
- Hikari：minimum-idle 5 / maximum-pool-size 20 / connection-timeout 5000
