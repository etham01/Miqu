# Miqu 性能测试方案（JMeter）

> 适用版本：JMeter 5.6.3+ ｜ 被测后端：`http://localhost:8081`
> 配套数据文件：`tests/perf/users.csv`
> 编写目的：给 Miqu 社交系统做一轮完整的性能测试，产出可写进测试报告的结论。

---

# 第 0 步 ⚠️ 压测前必须先改的三处配置

**这一节不能跳过。** 不改的话，你压出来的是"日志打印的性能"，不是业务的性能——数字完全没有参考价值。

## 0.1 关掉 SQL 打印（最重要）

`application.yml` 里有一行：

```yaml
mybatis-plus:
  configuration:
    log-impl: org.apache.ibatis.logging.stdout.StdOutImpl
```

这是**开发期**用来在控制台看 SQL 的。压测时每条 SQL 都要往标准输出写一遍，CPU 和 IO 全耗在这上面。

**不用改文件**，启动时用命令行参数覆盖即可：

```bash
cd backend
mvn -DskipTests package
java -Xms512m -Xmx1g -XX:+UseG1GC \
  -jar target/miqu-backend-1.0.0.jar \
  --mybatis-plus.configuration.log-impl=org.apache.ibatis.logging.nologging.NoLoggingImpl \
  --logging.level.com.miqu=warn
```

## 0.2 把日志级别从 debug 降下来

同样是命令行覆盖（`--logging.level.com.miqu=warn` 已在上面那条命令里）。

## 0.3 堆内存要给够

`README.md` 里推荐的 `-Xmx320m` 是为**开发时省内存**用的。压测时请求量和对象创建量都大得多，这个堆会频繁 GC，测出来的响应时间会被 GC 拖长。

上一条命令里的 `-Xms512m -Xmx1g -XX:+UseG1GC` 就是压测用的配置。

> **别用 IDEA 直接跑压测**。IDEA 带调试器和热部署的开销。压测一律跑打好包的 jar。

# 第 1 步 测试目标

明确要回答这三个问题：

1. **单接口在无竞争时有多快？** —— 拿基线，后面所有数字都跟它比
2. **系统能撑到多少并发？** —— 找到 TPS 不再增长、响应时间开始陡升的那个拐点
3. **拐点在哪一层？** —— 是应用层、数据库连接池，还是 MySQL 本身

**明确不测的**：前端页面性能、静态资源加载、网络带宽。这次只测后端 API。

# 第 2 步 环境与数据准备

## 2.1 重置数据库

压测会产生真实数据（点赞、消息等），所以**压测前先重置**，保证数据量在可控范围：

```bash
mysql -u root -p < database/schema.sql
mysql -u root -p < database/data.sql
```

> 种子数据会给出确定的基础量：18 个普通用户、约 15 条动态等。
> 数据量固定，两次压测之间才有可比性。

## 2.2 确认后端已启动且数据库正常

```bash
curl http://localhost:8081/api/health
# {"code":200,...,"data":{"status":"UP","application":"miqu","database":"UP"}}
```

**必须看到 `database: UP`。** 如果这里是 DOWN，压测跑出来的全是 500，白压。

## 2.3 测试账号

`tests/perf/users.csv` 里是 18 个种子账号（`test001` ~ `test018`，密码都是 `123456`）。

**为什么不建议压测时批量注册新账号？**
- 注册本身是写操作，会污染压测结果
- 而且项目**没有删除用户的接口**，注册出来的账号会永久留在库里

18 个账号配合"循环读取"完全够用——压测关心的是并发压力，不是账号数量。

## 2.4 确定压测机与后端的关系

| 并发规模 | 部署方式 | 说明 |
|---|---|---|
| ≤ 50 线程 | 本机跑 JMeter + 后端 | 方便，但两者抢 CPU，绝对值会偏低 |
| > 100 线程 | **JMeter 与后端分开两台机器** | 否则压出来的瓶颈是压测机自己 |

**JMeter 自身也是会打满的。** 本机跑的时候，如果看到 JMeter 进程 CPU 100%，说明瓶颈在压测机，结论无效。

# 第 3 步 JMeter 元件清单（照着搭）

打开 JMeter，按下面的顺序添加。**每一项的配置都写清楚了，照着填。**

## 3.1 测试计划（Test Plan）

先在最外层加**用户定义的变量**，这样后面所有地方都能复用，改压力只改一处：

| 变量名 | 值 | 说明 |
|---|---|---|
| `HOST` | `127.0.0.1` | 后端地址 |
| `PORT` | `8081` | **注意不是 8080**（8080 被本机 Windows 服务占用） |
| `THREADS` | `50` | 并发线程数 |
| `RAMPUP` | `10` | 多少秒内把线程全部启动 |
| `DURATION` | `180` | 持续压测时长（秒） |

## 3.2 HTTP 请求默认值

右键测试计划 → 添加 → 配置元件 → **HTTP 请求默认值**

| 字段 | 值 |
|---|---|
| 协议 | `http` |
| 服务器名称或 IP | `${HOST}` |
| 端口号 | `${PORT}` |
| 内容编码 | `UTF-8` |
| 实现 | `HttpClient4` |
| 连接超时 | `5000` |
| 响应超时 | `15000` |

## 3.3 HTTP 信息头管理器（放在测试计划级）

右键测试计划 → 添加 → 配置元件 → **HTTP 信息头管理器**

添加两行：

| 名称 | 值 |
|---|---|
| `Accept` | `application/json` |
| `Content-Type` | `application/json; charset=UTF-8` |

> ⚠️ **不要把 `Authorization` 加在这里。** 否则登录接口也会带上一个空的 Bearer 头。
> 认证头要单独加在业务请求下面，见 3.6。

> 💡 也不需要一个 Cookie 管理器。本项目用 JWT，身份信息走 `Authorization` 头，不依赖 Cookie。

## 3.4 CSV 数据文件设置

右键线程组 → 添加 → 配置元件 → **CSV 数据文件设置**

| 字段 | 值 |
|---|---|
| 文件名 | `tests/perf/users.csv`（建议填绝对路径） |
| 文件编码 | `UTF-8` |
| 变量名称 | `username,password` |
| 忽略首行 | `True` |
| 分隔符 | `,` |
| 遇到文件结束符再次循环 | `True` |
| 遇到文件结束符停止线程 | `False` |
| 线程共享模式 | `当前线程` |

> **"线程共享模式 = 当前线程"**：这样每个线程在整个压测过程中固定用同一个账号，
> 更接近真实用户的一次会话。

## 3.5 线程组

右键测试计划 → 添加 → 线程（用户）→ **线程组**

| 字段 | 值 |
|---|---|
| 名称 | `混合业务场景` |
| 线程数 | `${THREADS}` |
| Ramp-up 时间 | `${RAMPUP}` |
| 循环次数 | 勾选 **调度器**（下面的"持续时间"才生效） |
| 持续时间 | `${DURATION}` |
| 启动延迟 | `0` |

## 3.6 登录（每个线程只执行一次）

**这是整个脚本最关键的一段。** 里面的请求：

① 右键线程组 → 添加 → 逻辑控制器 → **仅一次控制器（Once Only Controller）**

② 在它下面加 → 取样器 → **HTTP 请求**

| 字段 | 值 |
|---|---|
| 名称 | `登录` |
| 方法 | `POST` |
| 路径 | `/api/auth/login` |
| 消息体数据 | `{"username":"${username}","password":"${password}"}` |

③ 在"登录"下面加 → 后置处理器 → **JSON 提取器（JSON Extractor）**

| 字段 | 值 |
|---|---|
| 变量名称 | `token` |
| JSON Path 表达式 | `$.data.token` |
| Match No. | `1` |
| 默认值 | `NOT_FOUND` |

④ 在"登录"下面加 → 断言 → **JSON 断言**

| 字段 | 值 |
|---|---|
| JSON Path | `$.code` |
| 期望值 | `200` |

⑤ **认证头**：右键"登录"→ 添加 → 配置元件 → **HTTP 信息头管理器**，加一行：

| 名称 | 值 |
|---|---|
| `Authorization` | `Bearer ${token}` |

> ⚠️ 这个头管理器的作用域是它所在的层级及以下。放在"登录"下面只会影响登录这一个请求。
> **所以业务请求（3.7）每个都需要自己的头管理器**——或者把带 `Authorization` 的头管理器
> 放在"仅一次控制器"之外、线程组之内，让它作用于所有业务请求。
> **推荐后者**：先放一个全局的 `Authorization` 头管理器在最上面，再把登录那个请求单独排除
> （用 3.7 的控制器结构即可）。

## 3.8 思考时间（定时器）

没有思考时间的压测，等于让虚拟用户以机器的速度疯狂点击，结果没有参考价值。

在线程组下 → 添加 → 定时器 → **高斯随机定时器（Gaussian Random Timer）**

| 字段 | 值 |
|---|---|
| 偏差（Deviation） | `300` |
| 固定延迟偏移 | `700` |

效果：每次请求之间随机停顿约 **0.4 ~ 1.0 秒**，模拟真人看一会儿再点。

> 这个定时器会作用于线程组内每个取样器，包括登录。登录时多等一次无关紧要。

## 3.9 监听器

**只加这两个**：

- 聚合报告（Aggregate Report）
- 汇总报告（Summary Report）

> ⚠️ **压测时绝对不要开"察看结果树（View Results Tree）"**。它会把每个请求的
> 请求/响应内容全部存进内存，几百个线程几分钟就能把 JMeter 撑爆，而且会严重拖慢压测机。
> 只在**调试脚本**的时候临时打开，确认没问题后立刻删除。

# 第 4 步 ⚠️ 本项目最容易踩的坑：断言必须查响应体的 code

**这是 Miqu 这个项目做性能测试时最容易犯的错，而且错了不会报错，只会让你拿到一份假数据。**

本项目有一条贯穿所有接口的全局约定：

> **HTTP 状态码恒为 200，业务结果放在响应体的 `code` 字段里。**

也就是说：
- 参数错误 → HTTP **200**，body 里是 `{"code":400,...}`
- 未登录 → HTTP **200**，body 里是 `{"code":401,...}`
- 系统异常 → HTTP **200**，body 里是 `{"code":500,...}`

### 所以：

| ❌ 错误做法 | ✅ 正确做法 |
|---|---|
| 用默认的"响应状态码 = 200"断言 | 用 **JSON 断言**，JSON Path 填 `$.code`，期望值填 `200` |
| 看到"错误率 0%"就以为一切正常 | 实际可能全是 400/401/500，只是 HTTP 状态是 200 而已 |

**如果只断言 HTTP 状态码，你会得到一份"错误率 0%、TPS 很高"的完美报告——而它完全是假的。**

### 点赞场景的断言要放宽

点赞接口在"已经点过赞"时返回 **409**（不是错误，是业务规则）。而我们的压测脚本是多个线程
反复点同一条动态，必然会撞上重复点赞。

所以点赞的 JSON 断言这样配：

| 字段 | 值 |
|---|---|
| JSON Path | `$.code` |
| 勾选 | **匹配为正则表达式** |
| 期望值 | `200|409` |

含义：返回 200（点赞成功）或 409（已点过赞）都算正常，只有其他值才算失败。

> 真实生产环境的压测里，写接口的断言通常都要这样放宽。
> **但要在报告里明确写出来**——"点赞场景有 X% 返回 409，属预期业务行为，不计入错误率"。
> 这也是为什么第 5 轮要单独做一个"并发点赞"专项来验证唯一性。

# 第 5 步 分五轮执行

**不要一上来就 200 线程压 30 分钟。** 按下面顺序逐轮加深，每轮都有明确的产出。

## 第 1 轮：基准测试（Baseline）

| 参数 | 值 |
|---|---|
| 线程数 | `1` |
| 持续时间 | 每个接口 60 秒 |
| 目的 | 拿到"无人竞争时"的响应时间基线 |

**产出**：每个接口的 P50 / P90 / P95 / P99。**后面所有轮次的数字都跟这组比。**

## 第 2 轮：单接口阶梯加压，找拐点

固定压**一个**接口（建议选 `GET /api/posts`，它是最核心的读接口），线程数阶梯上升：

| 档位 | 线程数 | 每档时长 |
|---|---|---|
| 1 | 10 | 3 分钟 |
| 2 | 20 | 3 分钟 |
| 3 | 50 | 3 分钟 |
| 4 | 100 | 3 分钟 |
| 5 | 200 | 3 分钟 |

**怎么读结果**：

| TPS 表现 | 响应时间表现 | 结论 |
|---|---|---|
| 稳定上升 | 基本不变 | 还没到拐点，继续加压 |
| **停止上升** | **开始陡升** | **← 这就是拐点，记下来** |
| 开始下降 | 大幅上涨 | 已经过载，不用再往上加了 |

**拐点前的最大 TPS**，就是这个接口在当前环境下的容量上限。

## 第 3 轮：混合业务场景

用 3.7 搭好的脚本，按 60/20/15/5 的比例混合请求。

| 参数 | 值 |
|---|---|
| 线程数 | 取第 2 轮拐点的 **70%** |
| 持续时间 | 10 分钟 |

**产出**：真实业务形态下的 TPS 与响应时间，以及**各接口分别的耗时占比**（聚合报告里按 label 看）。

## 第 4 轮：稳定性测试（Soak Test）

| 参数 | 值 |
|---|---|
| 线程数 | 取第 2 轮拐点的 **50%** |
| 持续时间 | **30 ~ 60 分钟** |

**看什么**：

- 响应时间是否**随时间逐渐变长**（阶梯上升 = 有内存泄漏或资源未释放）
- 后端进程的内存占用是否持续增长且不回落
- 数据库连接数是否稳定

**这一轮专门用来发现"跑一会儿就慢下来"的问题**，短时间压测发现不了。

## 第 5 轮（加分项）：并发点专项

Miqu 有一条很有意思的业务规则：**同一条动态不能重复点赞**（靠数据库唯一键兜底）。

测试方法：

| 参数 | 值 |
|---|---|
| 线程数 | `50` |
| Ramp-up | `0`（**让 50 个线程在同一瞬间发出请求**） |
| 循环次数 | `1` |
| 目标 | 同一个账号、同一瞬间、对同一条动态点赞 |

**预期结果**：只有 **1 个**请求返回 200，其余全部返回 409；数据库里 `post_like` 只增加 **1 行**。

**验证 SQL**：

```sql
SELECT COUNT(*) FROM post_like WHERE post_id = 1 AND user_id = 2;
```

**这一轮为什么有价值**：它验证的是**并发正确性**，不只是性能。很多系统在低并发下功能正常，
一到并发就出现重复数据或计数错乱。这是性能测试里最能体现测试深度的一项。

# 第 7 步 瓶颈定位：数字不好看的时候往哪查

这是性能测试真正的价值所在——**找到瓶颈，而不只是报个数字**。

## 7.1 按现象排查

| 现象 | 最可能的原因 | 怎么验证 |
|---|---|---|
| TPS 上不去，但后端 CPU 不高 | **数据库连接池打满** | 见 7.2，本项目最可能就是这个 |
| TPS 上不去，后端 CPU 100% | 应用层计算瓶颈（序列化、加解密） | 用 JProfiler / arthas 看热点方法 |
| TPS 上不去，JMeter 自身 CPU 100% | **压测机不够** | 换一台机器跑 JMeter |
| 响应时间随线程数线性增长 | 排队，未到过载 | 属正常现象 |
| 错误率突然上升 | 连接池等待超时或数据库拒绝 | 看后端日志有没有超时报错 |

## 7.2 本项目最可能的瓶颈：Hikari 连接池只有 20

`application.yml` 里：

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20
```

**这意味着同一时刻最多只有 20 个请求能拿到数据库连接**，第 21 个请求要排队等。

所以在找拐点时，如果看到 **TPS 在 20 线程附近就不再明显增长**，八成就是撞到连接池了。

**验证方法**：

```sql
-- 另开一个窗口，压测过程中反复执行
SHOW PROCESSLIST;
-- 如果看到大量连接处于 Sleep / Query 状态，且总数接近 20，就是连接池打满了
```

**这时候该怎么办**（这是报告里最值钱的一段）：

不要直接调大连接池就完事，要**分情况讨论**：

| 情况 | 结论 |
|---|---|
| 数据库 CPU 还有富余 | 可以把 `maximum-pool-size` 调大，重新压，看 TPS 能否继续上升 |
| 数据库 CPU 已经很高 | **连接池不是瓶颈，数据库才是**。调大只会让数据库更慢。该考虑加索引、优化慢查询 |
| 连接池没打满但 TPS 也不涨 | 瓶颈在别处，回到 7.1 继续排查 |

**这一段体现的正是"会分析"和"只会跑脚本"的区别。**

## 7.3 进阶：配合后端观测

压测时同时开一个窗口观察：

```bash
# Windows：看 Java 进程的 CPU 和内存
tasklist /FI "IMAGENAME eq java.exe"

# 或直接用 jconsole / jvisualvm 连上去看堆和线程
```

# 第 8 步 常用命令

## 8.1 正式压测要用非 GUI 模式

JMeter 的图形界面本身非常吃资源。**搭脚本和调试时用 GUI，真正跑压测时必须用命令行模式**：

```bash
# 非 GUI 模式跑，结果存成 jtl
jmeter -n -t miqu.jmx -l result.jtl

# 跑完自动生成 HTML 报告
jmeter -n -t miqu.jmx -l result.jtl -e -o report/

# 跑完直接打开 report/index.html 看图表
```

参数说明：
- `-n` 非 GUI 模式
- `-t` 测试计划文件
- `-l` 结果文件（如果文件已存在会报错，先删掉）
- `-e -o` 生成 HTML 报告到指定目录（目录必须为空）

## 8.2 用命令行参数调整压力，不用改脚本

在 JMeter 里把线程数写成 `${__P(threads,50)}` 这种形式，就能从命令行传入：

```bash
jmeter -n -t miqu.jmx -Jthreads=100 -Jduration=300 -l result.jtl
```

这样一份脚本可以反复跑不同压力，不用每次去改图形界面。

# 第 9 步 常见问题

| 问题 | 原因与处理 |
|---|---|
| 所有请求都返回 401 | 登录没成功，或 `Authorization` 头没生效。**先在"察看结果树"里看登录请求返回的 token 是否提取到了** |
| 所有请求返回 400 | 大概率是 `Content-Type` 没设成 `application/json` |
| 错误率 0% 但你怀疑不对 | **检查断言是不是只查了 HTTP 状态码**——见第 4 节 |
| 报"Address already in use" | 后端没起来，或端口填成了 8080 |
| 连接被拒绝 | 后端没启动，或 `HOST`/`PORT` 写错 |
| 压测后数据乱了，影响自动化测试 | 重置数据库：`mysql < schema.sql; mysql < data.sql` |
| JMeter 越跑越慢 | 检查是不是开了"察看结果树" |

# 附录：为什么这样设计

| 设计决策 | 理由 |
|---|---|
| 先测基线再阶梯加压 | 没有基线，就无法判断后面的响应时间变慢是"变慢"还是"本来就这样" |
| 混合场景按 60/20/15/5 | 社交产品是读多写少。如果全压写接口，测出来的是不真实的负载结构 |
| 一定要加思考时间 | 不加的话是机器速度而非人的速度，TPS 会虚高，没有参考价值 |
| 登录只执行一次（仅一次控制器） | 真实用户不会每个操作都重新登录。反复登录会把压力错误地集中在认证接口上 |
| 断言查 body 的 `code` 而不是 HTTP 状态 | 本项目 HTTP 恒为 200，只看状态码会拿到假的 0% 错误率 |
| 单独做一轮并发点赞专项 | 验证的是**并发正确性**，而不只是性能——这是性能测试里最容易被忽略、也最有价值的一环 |
| 单独做一轮稳定性测试 | 内存泄漏、连接泄漏这类问题只有跑得够久才会暴露 |
