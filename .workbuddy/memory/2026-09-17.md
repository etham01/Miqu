### 最重要的三条实测结论

1. 🔴 **认证层（拦截器）压过参数层（Bean Validation）**
   禁用账号 + 空 avatar → **423**（不是 400）。
   机制：`preHandle` 在参数解析**之前**。这条之前无人记录。
2. 🔴 **通知撤回是逻辑删除**
   `Notification extends BaseEntity` → `delete` 实为 `UPDATE deleted=1`。
   实测：取消关注后该行**仍在**（id=38, deleted=1）；而同一操作的 `follow` 行是**物理删除**（count=0）。
3. 🔴 **处理不存在的举报返回 404**（不是 400）
   `BizException.of(ErrorCode.NOT_FOUND, "举报不存在")` —— code 取 NOT_FOUND 自带的 404。
   → 这是**修掉的一个真实记录错误**。

## 三、修掉 3 个"根本无法解析"的 YAML（重要）

抽取完成后跑了一遍全量 `yaml.safe_load`，发现 3 个文件是**坏的**：

| 文件 | 真因 |
|---|---|
| `business_rules.yaml:94` | **`or` 作为流式映射的键**会让 PyYAML 6.0.3 直接炸（`and`/`not` 不会；`on` 会静默变布尔 `True`） |
| `data_model.yaml:249` | 值里内嵌裸 ASCII 双引号 |
| `endpoints.yaml:659` | `test_implication` 缩进比同级键多 2 空格，被当成序列元素 |

**判据来源**：我用隔离测试确认了 `{a: 1, or: 2}` 失败、`{a: 1, and: 2}` 成功 —— 没猜。
