## 任务：排查「头像图片无法加载」（只读诊断，未改任何代码）

产出 `docs/testing/avatar-issue-diagnosis.md`。结论如下。

### 核心结论：头像代码链路是好的，"加载不出来"的直接原因是**没有失败兜底**

`frontend/src/components/UserAvatar.vue` 只有 `v-if="src"`（判断"有没有值"），
**没有 `@error`**（不判断"能不能加载出来"）→ URL 非空但取不到图时**永久破图**，
既不降级到首字母占位、也不会恢复。

**关键点：全项目 15 处头像渲染共用这一个组件**
（`DefaultLayout` / `PostCard` / `CommentList` / `PostEditor` / `UserCard` /
`MessageView` / `NotificationView` / `AdminLayout` / 5 个后台管理页），
所以一处出问题 → **全站头像一起挂**，表现完全就是"头像功能异常"。

### 本轮实测到的 3 个真实缺陷

| 编号 | 缺陷 | 位置 | 级别 |
|---|---|---|---|
| BUG-006 | 头像加载失败无兜底，永不降级到首字母占位 | `UserAvatar.vue`（15 处共用） | **P1** |
| BUG-007 | 静态资源 404 被包成 `HTTP 200 + application/json`，`<img>` 解码失败 | `GlobalExceptionHandler` | P2 |
| BUG-008 | 头像接口不校验目标文件是否存在，可写入指向不存在文件的路径 | `UserServiceImpl.updateAvatar` | P2 |

复现证据见诊断报告：设一个"前缀合法但文件不存在"的头像 →
`http=200 content-type=application/json` → Chrome 里 2 个 `<img>` `naturalWidth=0`、
占位 span = 0；截图 `.workbuddy/screenshots/avatar-broken-fallback.png`。

> BUG-008 与上一轮的 BUG-005 是同一方法的两半：005 补了"来源前缀"校验，
> 008 是没收的"文件真实存在"校验。当时有意收窄范围，现在看该补。

### 已排除的可能（避免下次重复排查）

- **20 个种子头像的外链 `i.pravatar.cc` 当前网络下全部可达**（逐个拉取，200 image/jpeg，3.4–7.5KB）

### 数据侧事实（演示前该清理）

- `uploads/` 下 42 个文件**全是 pytest 造的 20/22/24 字节"魔术字节占位文件"**，不是真图。
- 库里 3 个账号的 avatar 指向 `/uploads/...`：`id=237` 指向不存在的
  `qa-avatar.jpg`（pytest 写入的字符串，从未真正上传）→ **此刻就是破图**。
- 216 个空头像 + 20 个外链头像 + 3 个本地头像（其中 2 个是本次诊断造的）。

### 环境坑（新踩到，务必记住）

**bash 里用 `curl -o /dev/null` 或把 curl 放进 `while read` 循环，会批量返回 `000`/0 字节**，
报 `curl: (23) client returned ERROR on write` 或直接静默失败。
这是**沙箱写输出的假象**，不是网络问题——我差点据此误判"图床全挂了"。
**正确做法：单个 curl 写真实文件，或用 Node 的 fetch 在单进程里顺序验证**
（已沉淀为 `.workbuddy/tools/check_seed_avatars.mjs`）。

| 文件 | 改动 | Bug |

**BUG-006 的关键认知**：全站 15 处头像都渲染 `UserAvatar`（没有第二处自行拼 `<img>`），
所以兜底只需做在这一层，一处修复全站生效。`watch(props.src)` 那句是必要的——
否则用户换成新头像后会一直停在失败态。

**BUG-007 的边界**：这是**有意偏离**「HTTP 恒 200」项目约定的**唯一例外**，
只对 `/uploads/**` 生效；`/api/**` 契约完全没动，并加了对照用例
`test_unknown_api_path_keeps_http_200` 防止后人把例外推广出去。

### BUG-008 为什么没改（重要，下次别重复踩）

修法只有 5 行，但会打破 **2 条既有用例**——它们引用的路径磁盘上都不存在：
- `tests/api/test_user.py::test_update_avatar` → `/uploads/.../qa-avatar.jpg`（不存在，断言 200）
- `UserControllerTest#updateAvatar_success` → `/uploads/.../newavatar.jpg`（不存在，断言 200）

即这两条用例**把"可以设置不存在的文件"当成了预期行为**。按项目纪律停下上报，
给了三个方案（A 改用例为先真上传 / B 只防目录穿越 / C 登记为缺口），等用户拍板。

### 顺手修掉一个既有潜在缺陷（与本次改动无关）

**`test_cases/*.yaml` 有 4 处 YAML 语法错误**：`steps: [并发 POST /api/users/{id}/follow]`
——`{` 在流式序列里是非法构造。之前一直没被发现，是因为当时机器上**没装 PyYAML**，
`check_consistency.py` 走了正则兜底分支；PyYAML 装上后真解析就崩了。
已给这 4 行加引号，并让校验器把 `yaml.YAMLError` 当**问题**报出来（退出码 1），
而不是让栈冒到用户面前。
